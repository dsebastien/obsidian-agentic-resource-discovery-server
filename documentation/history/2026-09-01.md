# 2026-09-01

Two small API fixes found while using the registry from a Claude Code session that boots with no skill registry and discovers skills through the MCP endpoint instead (~48K vs ~98K tokens at session start on a 415-skill vault).

## Done

### `POST /search` honours `limit`

- Only the ARD spec's `pageSize` was parsed; a top-level `limit` — the name the MCP `search` tool, `/explore` and the Code Mode `registry.search(query, { limit })` all use — was stripped by `z.object` and the default page of 10 came back silently. `limit` is now an alias; `pageSize` wins when both are sent. `ArdSearchRequest` carries it too.
- The MCP `search` tool clamps `limit` to the same 1–100 integer contract (it accepted any number before).
- Tests use a spy backend that records the forwarded `limit` — the first version of the test searched a term with exactly one fixture hit and would have passed against the old code (caught by an adversarial review).

### `GET /status` (bearer-authed)

- `{ status: ok|degraded, catalog: { entries }, search: { backend, ready, embeddings: { state, ready } | null } }`. Semantic backends serve lexical-only results while their index builds and a client had no way to tell; now it can wait on `embeddings.ready`. `degraded` = no index yet or embeddings `failed`. Always HTTP 200.
- Test drives a backend whose `embeddingState` is a real getter and walks `building → ready → failed` across requests.

## Adversarial review (Codex gpt-5.6-sol, xhigh)

Acted on: false-positive limit test, `/status` never consulting `isReady()`, MCP/REST limit contract mismatch, `ArdSearchRequest` missing the alias, `Object.create`+`Object.assign` not exercising a getter, missing history entry.

Deliberately not acted on:

- `{ pageSize: 1, limit: 0 }` → 400 although the winning value is valid. Invalid input is invalid; documenting the precedence is enough.
- Strict (`.strict()`) request validation. The pinned ARD entry/request schemas keep `additionalProperties: true` for `@context`-driven extension; rejecting unknown keys would break conformant clients to protect against typos.
- `pageToken` / `federation` accepted but unimplemented on `/search` — pre-existing, real, tracked separately (results are capped at one page today).

## Subagent definitions as a second catalog family (shipped the same day)

Implemented the revised plan end to end; all four milestones in one pass because M1 turned out to be the seam the rest needed.

- `src/app/scan/frontmatter.ts` — the untrusted-frontmatter normaliser extracted from the skill enricher (`asString`, `asStringArray`, `asFlag`, `asToolList`, `deriveToolTags`). Skills switched over; the only observable change is two new tool tags (`uses-skills`, `spawns-agents`) on skills that list `Skill` / `Agent`.

Both families register their artifacts; `get_resource` / `get_skill` and the `/subagents/*` route resolve through it. Serve re-checks `realpath` against the scan root and a 1 MB cap, so a symlink swapped in after the scan is refused. - `ScanSnapshot` + `RegistryController.setScannedEntries()` — one rebuild, one index, both families; `setSkillEntries` kept as an adapter. Coordinator runs both scans before publishing either; a throwing agent scan leaves the previous catalog intact (spec).
- Watcher takes `{ folder, family }` targets: `SKILL.md` at any depth for skill roots, top-level `.md` for subagent roots.
- Settings: `agentFolders` (default `[]`, opt-in — BR-16), `lastScanStats.agentCount`; settings tab has a "Subagent folders" list with the public-exposure note; the rescan button covers both.
- `/status.catalog` is now `{ entries, skills, subagents, manual }`.
